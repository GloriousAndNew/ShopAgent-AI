# 开发顺序与步骤：每次只完成一关

这份文档告诉你“先做什么、具体做哪些步骤、怎么知道做对了”。第一天的详细命令见 [操作手册](./02-第一天操作手册.md)；遇到概念不懂，查 [学习文档](./03-零基础学习文档.md)。

正式 Mock MVP 已于 2026-10-09 实现，代码放在 `shopagent/`，与学习练习分开。下面的关卡可以用于逐步学习和复现；云模型为后续阶段。实现中的实际文件及启动方式以根目录 README 和 MVP 新手使用说明为准。

## 开发顺序总表

| 关卡 | 先学会 | 实际做的东西 | 通过后你能做什么 |
|---|---|---|---|
| 0 | 运行文件、保存文件、终端 | hello.py、虚拟环境 | 改代码后自己运行 |
| 1 | 列表、字典、if、for、函数 | 商品筛选练习 | 用程序找到预算内商品 |
| 2 | 请求、接口、JSON | 商品查询 API | 浏览器能查商品 |
| 3 | 模块、接口约定、错误 | 正式目录、统一契约、假插件 | 主程序按约定调用一个模块 |
| 4 | SQL、数据库、数据校验 | 商品插件和数据库 | 重启程序后商品仍在 |
| 5 | 用户身份、权限 | 登录、订单模块 | 登录用户只能查自己订单 |
| 6 | 调接口、超时、失败处理 | 物流模块 | 查订单后查物流；物流失败不影响商品 |
| 7 | 文件读取、检索、引用 | 政策知识模块 | 有依据地回答售后规则 |
| 8 | 状态、确认、事务、幂等 | 售后申请模块 | 确认后创建一张模拟申请单 |
| 9 | 网页结构、按钮、请求 | 聊天页和 Mock 编排 | 不依赖模型也能演示业务闭环 |
| 10 | 模型调用、结构化参数 | 云模型适配 | 自然语言提问能触发正确业务 |
| 11 | 进程、健康检查、版本 | 插件 worker、管理页 | 主程序运行中启停和替换插件 |
| 12 | 自动检查、记录、复现 | 验收集和启动手册 | 别人按说明也能跑起来 |

第 3 关就约定模块边界，第 11 关才实现完整热插拔。这样前期练习容易理解，后期也有明确接口可用。中途使用进程内模块只是过渡，不计为热插拔验收。

## 第 0–2 关：先做小练习

### 第 0 关：我能运行代码

按第一天手册第 1–4 步做。通过标准：改 hello.py 的中文、保存、运行，输出跟着改变。理解代码写在文件里，命令写在终端里。

### 第 1 关：代码能筛选商品

1. 打开 `learning_examples/product_filter.py`。
2. 看懂 PRODUCTS 中的 3 个商品，每个有 ID、名称、价格。
3. 从终端运行：`py -3.13 -X utf8 .\learning_examples\product_filter.py`。
4. 将预算从 `20000` 改成 `10000` 再运行。
5. 加一个 79 元、名为“耳机收纳包”的商品，ID 使用 P004。
6. 把预算改为 `5000`，观察空结果。

通过标准：原始 200 元预算找到耳机和鼠标；100 元只找到鼠标；新增收纳包后 100 元能找到鼠标和收纳包。你能解释为什么 299 元键盘没有入选。

### 第 2 关：把筛选函数接到浏览器

按第一天手册第 5–10 步做。打开 first_api.py，找出 `/products` 调用 `search_products` 的位置。它展示了“接口接收预算 → 业务函数筛选 → 接口返回数据”。

通过标准：能独立启动、停止服务；在 `/docs` 输入不同预算得到正确结果；知道 JSON 是数据，当前还不是完整网页。

## 第 3 关：正式项目骨架和模块约定

要创建：`shopagent/app/main.py`、`shopagent/contracts/models.py`、`shopagent/core/registry.py`、`shopagent/core/model_provider.py`、`shopagent/plugins/demo/`。目录作为 Python 包使用时添加 `__init__.py`。

步骤：

1. 在新目录中创建正式宿主程序和 `/health`，保留学习例子不动。
2. 在 contracts 中定义插件说明：ID、版本、契约版本、能力列表、依赖列表。
3. 定义工具请求：工具名、参数、request_id、身份上下文；工具结果统一为成功数据或错误码。
4. 用 Pydantic 检查类型和必要字段，缺字段时返回清楚的错误。
5. 做一个 demo.echo 假插件：传入文字，原样返回。先在进程内运行。
6. 注册表记录有哪些可用能力；宿主通过注册表找工具，避免直接写死某个插件的业务实现。
7. 做 MockModelProvider：预先约定几个问题对应哪些工具，并在回复标明模拟模式。
8. 日志记录请求 ID、模块名、结果和耗时。

通过标准：有假插件时能调用 echo；没有插件时主程序仍正常运行并明确说能力不可用；随意传缺字段参数不会悄悄成功。

为什么先做它：约定统一插头尺寸，后面每个部门按同一种插头接入。

## 第 4 关：商品插件与持久化

要创建：`plugins/product/service.py`、`repository.py`、`manifest.json`、`README.md`，以及初始化数据脚本。数据放 `data/product.db`。

步骤：

1. 建 products 表和 skus 表，SKU 表包含款式、库存和更新时间。
2. 先导入练习中的 3 个商品，验证后再扩到约 30 个商品、60 个 SKU。
3. 写数据访问函数：查询商品、详情和指定 SKU 库存；金额保存为整数分。
4. 写业务函数：search_products、get_product_detail、check_inventory。
5. 增加预算、属性、商品 ID 参数校验；无结果返回空列表，商品不存在返回 NOT_FOUND。
6. 将这些能力写到 manifest，通过注册表接入宿主。
7. 在商品插件自己的测试中验证过滤和 SKU 库存；此时不依赖订单模块。

通过标准：200 元以内的降噪商品没有超预算；黑色 SKU 与白色 SKU 库存不混；停止并重启后能查到原商品。

## 第 5 关：用户身份和订单模块

要创建：宿主的登录和认证代码；`plugins/order/`；`data/order.db`。

步骤：

1. 创建两个演示用户 A、B 和一个管理员，密码只用于本机演示；持久化时保存密码哈希。
2. 登录后签发有过期时间的身份令牌，宿主验证令牌后才能处理私有订单请求。
3. 建订单表和订单明细表，每个订单关联 user_id；给 A、B 各准备 5 个样本。
4. get_order_status 接收订单 ID，可信 user_id 来自认证上下文；同时查订单号和用户归属。
5. 不允许模型、浏览器直接指定“我现在是用户 B”。
6. 会话按用户及 session_id 隔离，用户只能读取自己的聊天历史。
7. 测未登录、A 查自己、A 查 B、B 查自己、令牌过期和不同会话。

通过标准：A 无法看到 B 的商品清单、金额和地址；订单插件再次校验归属；管理接口只允许管理员调用。

本关接口可独立测试，不需要先做完整聊天页面。演示用户的便捷切换只在 demo 模式出现。

## 第 6 关：物流模块与故障处理

要创建：`plugins/logistics/`、模拟轨迹数据、统一客户端超时处理。

步骤：

1. 为已发货订单生成模拟轨迹，明确数据是模拟的。
2. 宿主先通过订单模块验证归属，再把已授权订单上下文交给物流工具。
3. 物流模块返回轨迹、更新时间和可选预计时间；未知预计时间就留空。
4. 无物流号、未发货、记录缺失分别返回明确结果。
5. 加调用超时；只读调用最多重试一次。
6. 在注册表中暂时停用物流能力，验证商品及订单仍可调用。

通过标准：物流记录缺失时不会编造“明天到”；物流失败不导致整套接口退出。此时能力停用只是过渡版，独立进程和排空在第 11 关实现。

## 第 7 关：售后政策与证据检索

要创建：`plugins/knowledge/`、`data/policies/`，政策文件包含 ID、版本、生效日期和正文。

步骤：

1. 自行写 10–20 条“模拟店铺政策”，包括适用条件、例外和需要人工处理的情况。
2. 把政策按段落分成可引用的小块，每块保留来源和版本。
3. 先做简单关键词检索；按问题关键词找到相关段落。
4. search_policy 返回原文证据及版本，不只返回一个没有出处的结论。
5. 回复中显示引用；没有证据就说当前知识库无法确认。
6. 检查过期版本不参与当前规则判断；新旧政策冲突时不能随便选一个。

通过标准：回答能对应到具体政策；没收录的规则不会编造。第一版是关键词检索，有失败样本后再考虑向量检索。

## 第 8 关：售后申请闭环

要创建：`plugins/aftersale/`、`data/aftersale.db`、草稿和申请表、确认接口。

步骤：

1. 读取已授权订单和规则，写确定性的资格检查函数。
2. 信息不足时收集订单、商品、数量和原因。
3. prepare_return 只创建草稿，保存所依据的订单摘要和政策版本。
4. 展示草稿并等待用户确认，不能把“我想了解退货”理解成已确认提交。
5. 确认凭据绑定用户、草稿内容和有效期；修改草稿后重新确认。
6. confirm_return 提交时再检查条件，并在数据库事务中创建模拟售后单。
7. 使用幂等键和唯一约束防重复；重复点击返回同一申请结果。
8. 实现进度查询、取消草稿以及模拟转人工工单。

通过标准：确认前售后申请表没有新增申请；连续点确认两次只有一单；没有订单或规则能力时停止申请流程并提示。

这版创建的是申请单，不执行退款，不预约真实取件。能否退货由演示规则判断，不能直接套用原文案例结论。

## 第 9 关：聊天页面和 Mock 编排

要创建：`shopagent/web/`，聊天接口和会话记录，编排器。

步骤：

1. 做输入框、发送按钮和消息列表；先从宿主同一地址提供网页，减少跨域配置。
2. JavaScript 用 fetch 调聊天接口，显示等待中、结果和错误；先普通 JSON，再考虑流式输出。
3. 用 MockProvider 将几种固定问法映射到已经验证的工具；页面清楚显示 Mock 模式。
4. 实现 6 类意图及澄清兜底；缺订单号、商品指代不明确时先追问。
5. 用会话保存最近商品 ID、订单 ID，处理“第二款”和“这个订单”；歧义时不猜。
6. 显示商品卡片、订单卡片、政策引用、售后确认按钮和模拟转人工状态。
7. 网络失败时保留输入，售后重复请求依赖幂等处理。

通过标准：可以不用模型密钥演示商品、订单、物流和售后闭环；未知问法提示未支持，不能宣传它已具有真正的自然语言理解。

## 第 10 关：接入真正的模型

要创建：云模型 ModelProvider 实现、配置样例和调用记录。

步骤：

1. 到本关再选择一个能提供结构化输出或工具调用的模型服务，检查官方能力、接口和费用。
2. 密钥放本地环境变量或未提交的 .env 文件，不写在网页或版本库。
3. ModelProvider 接收问题、必要上下文和当前可用工具列表，返回结构化意图和参数。
4. 宿主对参数重新校验，拒绝未授权、已停用或不存在的工具。
5. 工具返回后，模型整理答案；价格、权限、售后资格和状态仍由程序决定。
6. 设置调用超时、次数上限和清楚的失败提示，记录真实调用量和费用。
7. 用固定测试问题和新的不同措辞对比 Mock 与云模型结果；记录误分类和错误参数。

通过标准：自然语言能完成 6 类场景；模型无法替用户跳过确认，也不能凭空改变订单状态。模型失败时明确说明原因；切换 Mock 要让用户知道。

## 第 11 关：把模块做成真正能热插拔的插件

要创建：每个插件的 worker.py、HTTP 适配器、生命周期管理器、插件配置和管理页。

步骤：

1. 让每个业务插件成为独立进程，提供 `/health`、`/manifest`、`/invoke` 三个接口；各自使用自己的数据库。
2. 不改业务函数，只把宿主调用换成 HTTP 适配器；插件间同样通过公开接口查询事实。
3. 插件服务绑定本机地址，内部请求带服务认证和宿主签发的身份上下文。
4. 宿主管理进程启动、健康检查、ready 状态和能力注册；仅接入配置白名单中的程序。
5. 管理页展示版本、依赖、状态和在途请求数量；普通用户不能管理插件。
6. 关闭时先禁止新请求进入，再等待正在进行的请求完成；超时后明确失败并回收进程。
7. 强依赖模块不能随意关闭：先提示依赖，也可选择按顺序级联停用。
8. 重新启动插件，健康检查通过后再恢复能力，不删除原数据库。
9. 每个请求固定使用注册表版本快照；执行工具时再次检查能力状态和权限。
10. 升级先启动不同端口的新版本，验证契约和健康后切换新请求；旧版本排空。新版未通过则保留旧版。
11. 保存期望开启状态，宿主重启后重新检查插件再公开能力。
12. 加一个 demo.echo 测试插件，通过注册接入，不修改宿主 API 路由。

通过标准：主程序不重启即可启停物流；已进入旧版的请求能结束；坏版本不能替换好版本；插件进程崩溃不影响商品等其他模块；数据库迁移等破坏性变化另做维护，不假装能无损热替换。

## 第 12 关：让结果可验证、可交付

步骤：

1. 建测试集：6 类业务各 6 个，加隔离 8 个、热插拔及故障 10 个、确认幂等 6 个，共 60 个。
2. 每个案例写输入、预期、实际结果、版本和耗时；另准备不同措辞的留出问题。
3. 关键的隔离、确认及幂等用例全部通过；业务正常用例按类别报告，目标至少 90%。
4. 做停用、重启、崩溃、超时、版本不兼容和升级失败演练。
5. 固定依赖，写初始化数据、启动和停止脚本，停止脚本只处理本项目记录的进程。
6. 写 README：需要什么、如何配置、如何启动、如何测试、如何演示、哪些功能仍是模拟。
7. 按 README 重新复现启动流程，再录制一段演示。

通过标准：另一个人能按手册启动并验证；你能解释一次问题从网页到工具再返回的全过程。

## 每关结束后怎么推进

先做本关最小样本，再扩大数据和情况。遇到失败先缩到最小例子，不要一口气改多个文件。

需要协助时，可以说明：“我做到第 X 关，运行了这条命令，预期是……，实际输出是……。请解释错误，修复后告诉我怎么验证。”每次实现一关，都应拿到文件变化、启动命令、解释和验收结果。
