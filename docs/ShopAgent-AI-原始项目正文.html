1.5 智能电商客服 Agent（ShopAgent AI）

推荐项目名称：以下名称均可在简历中使用，根据面试岗位侧重选择： - 通用名：ShopAgent AI 智能电商客服 Agent 系统 - 偏后端/架构：基于 A2A 多代理的电商智能客服平台 - 偏算法/数据：基于 LLM + MCP 的电商智能决策系统

一、项目背景

1.1 所属行业分类

电商零售 / AI 智能客服与导购。

1.2 为什么做这个项目

某头部电商平台年 GMV 超 500 亿，日均咨询量 10 万+，客服团队 200 人。过去客服基于关键词匹配回答，回答生硬且覆盖有限，用户满意度仅 65%。平台决定开发 AI 电商助手——ShopAgent AI，能够理解用户的购物需求，自动查询商品信息、订单状态、物流信息，提供个性化导购建议。

此前平台使用传统客服机器人，FAQ 匹配率低，复杂问题需转人工。技术部决定采用 AI Agent 架构，通过 MCP 对接商品系统、订单系统、物流系统，实现智能电商客服。

项目立项的核心驱动力是成本与体验的双重压力。200 人客服团队每年人力成本超 2000 万（按人均年薪 10 万计算），但用户满意度长期徘徊在 65%——用户吐槽"回答像机器人""问半天得不到答案"。更关键的是，大促期间（双11、618）咨询量暴涨 5-10 倍，客服团队根本扛不住，用户排队 30 分钟是常态，流失率高达 15%。

技术部调研后发现，传统客服机器人的问题在于只能匹配关键词，无法理解用户真实意图。用户问"有没有 200 以内的蓝牙耳机"，机器人只能匹配"蓝牙耳机"关键词，无法理解价格筛选条件；用户问"送妈妈什么礼物好"，机器人直接返回 FAQ 列表，无法结合用户画像做个性化推荐。

AI Agent 架构的优势在于：LLM 理解自然语言 + MCP 工具调用外部系统 + 多 Agent 协作处理复杂任务。用户说"我昨天下的订单什么时候到"，Agent 能理解这是"物流跟踪"意图，自动调用订单查询和物流跟踪工具，秒级返回结果。这种架构让系统既能处理简单查询（商品咨询、订单跟踪），也能处理复杂任务（退换货、个性化推荐），真正实现"像人一样理解用户需求"。

项目目标很明确：客服人力成本降低 50%，用户满意度提升到 85%+。通过 AI 助手处理 70% 的常规咨询，让人工客服专注处理复杂投诉和高价值客户，实现"人机协作"的最优配置。

1.3 项目的痛点

  1. 客服负载高：200 人客服团队应对日均 10 万+ 咨询，峰值排队 30 分钟
  2. 商品查询繁琐：客服需切换多个系统查询库存、价格、规格
  3. 订单跟踪慢：用户问订单状态，客服需手动查询物流系统
  4. 导购能力弱：传统机器人无法理解"适合送妈妈的礼物"等模糊需求
  5. 售后处理慢：退换货流程复杂，人工处理耗时长

1.4 项目的价值

  1. 7×24 智能客服：AI 助手全天候处理咨询，响应时间从分钟级降至秒级
  2. 商品信息秒查：MCP 工具对接商品系统，秒级返回库存、价格、规格
  3. 订单自动跟踪：MCP 对接物流系统，实时返回订单状态
  4. 智能导购：基于用户偏好和历史购买，个性化推荐商品
  5. 售后自动化：AI 引导用户完成退换货流程，减少人工介入

3.4.1 外部系统对接方式

本项目的 MCP 工具并不是自己造数据，而是对接甲方（电商平台）已有的业务系统。作为 Agent 开发工程师，我们的核心工作就是"把甲方的业务系统 API 包装成 LLM 能调用的 MCP 工具"。

① 外部系统是什么

甲方（电商平台）提供 4 类业务系统： - 商品系统：存储全平台商品的 SKU、价格、库存、规格参数、图文详情、用户评价 - 订单系统：存储用户的订单信息（下单时间、商品清单、支付金额、订单状态） - 物流系统：对接第三方物流（顺丰/圆通/中通等），提供运单轨迹、预计送达时间 - 用户行为系统：存储用户的浏览历史、购买记录、会员等级、偏好标签

② 甲方怎么给我们

甲方（电商平台技术部）提供： - RESTful API：每个业务系统暴露 HTTP 接口（如 GET /api/v1/orders/{order_id}） - OpenAPI 文档：Swagger 格式，描述每个接口的 URL、请求参数、响应结构 - 测试环境：独立的测试环境 + 测试账号，供我们联调 - 鉴权方式：AppKey + AppSecret 签名（每个请求 Header 带签名，防止接口被滥用）

③ 我们怎么包装成 MCP 工具

我们的工作分三步： 1. 写 Python 函数：用 httpx 异步调用甲方 API 2. 字段映射 + 格式转换：甲方的字段名（如 ord_status、logistics_name）对 LLM 不友好，我们要映射成中文友好字段（如 "订单状态"、"快递公司"）；甲方的状态码（如 ord_status=3）要翻译成可读文本（如 "已发货"） 3. 注册成 MCP 工具：用 @mcp.tool() 装饰器注册，LLM 就能通过自然语言调用

# 甲方 API：GET https://api.ec-client.com/v1/orders/{order_id}
# 鉴权：Header 带 AppKey + HMAC-SHA256 签名

import httpx
import hmac
import hashlib
import time
from fastmcp import FastMCP

mcp = FastMCP("ecommerce-mcp")

# 订单状态映射：甲方的数字编码 → LLM 友好的中文
ORDER_STATUS_MAP = {
    1: "待付款", 2: "待发货", 3: "已发货",
    4: "已签收", 5: "已取消", 6: "退款中"
}

def build_auth_headers(app_key: str, app_secret: str) -> dict:
    """构造鉴权 Header（AppKey + HMAC 签名）"""
    timestamp = str(int(time.time()))
    sign_str = f"{app_key}{timestamp}{app_secret}"
    signature = hmac.new(app_secret.encode(), sign_str.encode(), hashlib.sha256).hexdigest()
    return {
        "X-App-Key": app_key,
        "X-Timestamp": timestamp,
        "X-Signature": signature
    }

@mcp.tool()
async def get_order_status(order_id: str, username: str) -> dict:
    """查询订单详情（对接甲方订单系统）"""
    # 1. 用 httpx 调甲方 API
    resp = await httpx.AsyncClient().get(
        f"https://api.ec-client.com/v1/orders/{order_id}",
        headers=build_auth_headers(APP_KEY, APP_SECRET),

    )
    raw = resp.json()
    # 2. 字段映射：甲方的字段名 → LLM 友好的字段名

        "下单时间": raw["create_time"],

3.6 用户隔离机制

① 为什么需要隔离

电商场景下，多用户共用同一套 Agent 系统。如果不做隔离： - 用户 A 的订单查询可能返回用户 B 的订单（隐私泄露） - 用户 A 的购物偏好影响用户 B 的推荐（推荐不准） - 用户 A 的购物车数据混入用户 B 的会话（严重事故）

电商数据涉及《电子商务法》和《个人信息保护法》，隔离失败会导致用户流失和法律风险。

② ChatService 按 username 隔离

每个用户登录时携带 username（用户 ID），ChatService 内部用 functools.lru_cache + TTL 缓存为每个用户维护独立的 Agent 实例： - maxsize=100（最多同时缓存 100 个用户实例） - TTL=1800s（30 分钟无活动自动清理） - 不同 username 拿到完全独立的对话历史和 Agent 状态

③ MySQL 按 user_id 隔离

所有持久化数据表（chat_history、order_record、shopping_preference）都包含 username 字段，所有查询强制加 WHERE username = ? 条件。例如： - 查询订单：SELECT * FROM order_record WHERE username = 'user_456' - 查询偏好：SELECT * FROM shopping_preference WHERE username = 'user_456'

from cachetools import TTLCache

# 短期记忆：存当前会话对话历史
# maxsize=50 条消息，TTL=1800s（30 分钟无活动自动清理）
short_memory = TTLCache(maxsize=50, ttl=1800)

def add_message(username: str, role: str, content: str):
    """添加对话消息到短期记忆"""
    key = f"{username}_messages"
    if key not in short_memory:
        short_memory[key] = []
    short_memory[key].append({"role": role, "content": content})

def get_recent_messages(username: str) -> list:
    """获取最近对话历史"""
    return short_memory.get(f"{username}_messages", [])

import pymysql
from cachetools import TTLCache

class MemoryManager:
    """电商记忆管理器：短期（TTLCache）+ 长期（MySQL）"""

    def __init__(self):
        # 短期记忆：当前会话对话历史
        self.short_memory = TTLCache(maxsize=50, ttl=1800)
        # 长期记忆：MySQL 连接
        self.db = pymysql.connect(host="localhost", user="root",
                                  password="xxx", database="ecommerce")

    def get_memory(self, username: str) -> dict:
        """获取用户完整记忆（短期 + 长期合并）"""
        return {
            "recent_messages": self.short_memory.get(f"{username}_msg", []),
            "profile": self._query_profile(username),
            "recent_orders": self._query_recent_orders(username),
        }

    def _query_profile(self, username: str) -> dict:
        """查询用户画像（长期记忆）"""
        with self.db.cursor() as cur:
            cur.execute(
                "SELECT shopping_preference, clothing_size, default_address "
                "FROM user_profiles WHERE username = %s", (username,)
            )
            row = cur.fetchone()
            return dict(zip(["偏好", "尺码", "地址"], row)) if row else {}

    def _query_recent_orders(self, username: str, limit: int = 5) -> list:
        """查询最近订单"""
        with self.db.cursor() as cur:
            cur.execute(
                "SELECT order_id, product_name, amount FROM order_history "
                "WHERE username = %s ORDER BY created_at DESC LIMIT %s",
                (username, limit)
            )
            return [dict(zip(["订单号", "商品", "金额"], r)) for r in cur.fetchall()]

    def save_message(self, username: str, role: str, content: str):
        """保存对话到短期记忆"""
        key = f"{username}_msg"
        if key not in self.short_memory:
            self.short_memory[key] = []
        self.short_memory[key].append({"role": role, "content": content})

3.8 常见问题（面试常问）

Q1：电商场景下如何处理高并发咨询？

我们采用 LRU+TTL 缓存管理 ChatService 实例，最大 100 个实例，TTL 30 分钟。简单查询直接路由到对应 Agent，复杂问题才进入 Planning + ReAct。MCP 工具内部做了查询缓存，热门商品查询命中率 60%+。

Q2：如何实现智能导购？

RecommendAgent 通过 MCP get_user_profile 获取用户偏好和历史购买，通过 search_products 筛选符合条件的商品。Agent 内部有导购 prompt，能够理解"送妈妈的礼物""适合学生的平价耳机"等模糊需求，结合用户画像生成个性化推荐。

Q3：如何处理退换货等复杂售后？

复杂售后任务由 Planning Agent 生成执行计划：Step1: 验证订单 → Step2: 检查退换条件 → Step3: 生成退换单 → Step4: 安排物流取件。ReAct 循环逐步执行，每步观察结果后再决定下一步。

Q4：电商场景下 MCP 工具的并发压力怎么处理？

大促期间（双11、618），MCP 工具调用量是平日的 5-10 倍。应对措施：① 热门商品查询结果缓存 60 秒；② 订单/物流查询限流（单用户 10 次/分钟）；③ 非关键查询降级（如推荐列表延迟加载）。系统压测支持 500 QPS 并发。

Q5：为什么电商场景只用了 13 个 MCP 工具，比金融（15 个）少？

业务复杂度不同。金融场景需要风险评估、合规审查、投资组合分析等专业工具；电商场景核心是"查商品+查订单+推荐"三大块，工具数量精简。MCP 工具数量不是越多越好，够用、清晰、好维护最重要。

Q6：导购推荐的准确率是怎么评测的？

以实际购买作为 ground truth：用户对推荐商品的点击率、加购率、购买率。线上 A/B 测试：AI 推荐组 vs 传统关键词搜索组，购买转化率提升 35%。评测集 1000 条用户真实咨询。

Q7：用户隔离失效怎么办？

我们有监控告警：如果检测到用户 A 的查询返回了用户 B 的数据，立即触发告警并降级到人工客服。根因通常是缓存穿透或 SQL 漏写 WHERE 条件，通过代码审查和自动化测试规避。生产环境从未发生过隔离失效事故。

3.9 模型微调（可选）

⚠️ 本章节为可选内容。如果面试时被问到微调经验，可以参考本节回答。如果项目直接使用通用大模型 + Prompt Engineering 就能满足需求，也可以不做微调。

为什么要微调？

电商场景对模型的三个特殊要求，通用模型做不到：

  1. 意图识别更精准：本场景的 8 类意图（product_query / price_compare / inventory_check / order_query / logistics_track / return_apply / recommend_query / promotion_query）都是电商专有表达，通用模型（如 Qwen3-14B）在 zero-shot 下意图识别准确率约 85%，微调后可提升到 95%+
  2. 工具参数提取更规范：比如用户说"有没有 200 以内的蓝牙耳机，要降噪的"，要提取 {"keyword": "蓝牙耳机", "max_price": 200, "features": ["降噪"]} 这种结构化参数，微调后模型能更稳定输出符合 JSON Schema 的参数
  3. 情感分析识别用户投诉情绪：电商场景需要识别用户投诉情绪（如"这个耳机质量太差了，我要退货！"），通用模型容易忽略语气中的愤怒情绪，微调后能准确分类为"高优投诉"，触发优先处理流程

七、Agent Loop 适用性分析

7.1 为什么选择 Agent Loop

本项目采用 LangChain 的 Agent Loop（ReAct 循环）作为核心执行引擎，这是由本场景的业务特点决定的：

  1. 意图清晰且有限：本场景的意图共 8 类（product_query / price_compare / inventory_check / order_query / logistics_track / return_apply / recommend_query / promotion_query），每类意图对应的处理流程是固定的——比如"order_query"意图就是"提取订单号 → 调 MCP get_order_status → 整合状态返回"，LLM 不需要在多个分支之间反复跳转。
  2. 任务链短：绝大多数任务的步骤在 2-4 步之间，ReAct 循环足够处理。比如用户问"我昨天下的订单什么时候到"，Agent 只需要：① 调 MCP get_order_status(order_id="123456") → ② 调 MCP track_logistics(order_id="123456") → ③ 整合物流轨迹和预计送达时间返回。不需要长达 10+ 步的复杂规划。
  3. 步骤可预测：每一类任务的执行路径是确定的——查商品就是 search_products → get_product_detail，查订单就是 get_order_status → track_logistics，退换货就是 apply_return → get_return_status。不存在"根据前一步结果决定走完全不同的分支"这种复杂条件逻辑——而 LangGraph 的优势（动态条件分支、并行执行、状态机回环）在这种场景下是过度设计。
  4. 无强人机交互需求：本场景不需要"每一步都让用户确认再继续"的 human-in-the-loop 流程。用户问订单状态，Agent 查完直接返回；用户要退换货，Agent 一次性收集退货原因和取件方式即可。

💡 面试话术：面试官问"为什么不用 LangGraph"时，你可以回答——"我们的业务特点是意图清晰（8 类固定意图）、任务链短（2-4 步）、步骤可预测（每类意图走固定工具链），ReAct 循环完全够用。LangGraph 的优势是动态条件分支和并行执行，但我们的场景用不到这些，引入它会增加维护成本，属于过度设计。"

7.2 业务场景适配性

当然，本场景中也有一些"看似复杂"的任务，但我们通过简化业务流程使其适配 ReAct，而不是引入更复杂的执行引擎：

  1. "双11 秒杀并行库存检查看似要并行"的简化：用户说"帮我看看这 10 件商品还有没有货"，看似需要 10 次 check_inventory 并行调用。我们简化为串行：Agent 依次调用 10 次 check_inventory，每次都拿到结果再调下一次。实测 10 次串行调用总耗时 3-5 秒，用户体感与并行（<1 秒）差别不大，但系统复杂度大幅下降。
  2. "大额退款审批看似要条件分支"的简化：用户要退 2000 元的商品，按规则需要人工客服审核。我们不搞条件分支，而是把"是否需要审核"的判断下沉到 MCP 工具内部——apply_return 工具内部判断退款金额是否超过阈值（如 1000 元），返回结果里直接包含"需人工审核"或"已自动通过"的标识。Agent 只需要根据返回结果告知用户即可，不需要在 Agent 层写 if-else。
  3. "退换货收集信息看似要多轮人机交互"的简化：用户说"这个耳机有问题想退"，传统做法是"Agent 问订单号 → 用户答 → Agent 问退货原因 → 用户答 → Agent 问取件方式 → 用户答"3-4 轮交互。我们简化为一次性收集：Agent 在一条回复里把"订单号、退货原因、取件方式"三个选项一次性列出让用户填写，然后一次性调 apply_return 完成申请。从"4 轮交互"简化为"2 轮交互"（收集信息 + 完成申请），ReAct 循环轻松处理。

💡 一句话总结：ReAct 循环处理本场景 90%+ 的任务绰绰有余，剩下 10% 的"看似复杂"任务（并行库存检查、大额退款审批、退换货信息收集），我们通过简化业务流程（串行化 / 工具内部决策 / 一次性收集选项）让它也能用 ReAct 处理。这样既满足业务需求，又保持系统简单可维护——这正是工程上的务实选择。
