# 公网网关与服务器部署步骤

更新：2026-10-10。

目标：顾客打开 `https://你的域名/customer` 咨询，商家打开 `/merchant` 管理。当前完成的是代码保护和经过本机测试的部署模板，还没有公网服务器、域名与可信公网证书，因此还没上线。

## 先理解三个部分

顾客浏览器 → Nginx 网关（HTTPS、请求限制）→ ShopAgent 宿主（登录、Agent、人工回复）→ 独立业务模块。

Nginx 像门口：接收外部请求，把请求转给程序。HTTPS 加密顾客与门口之间的通信。ShopAgent 和独立模块只监听服务器自己的回环地址；公网不直接访问它们。

systemd 是 Linux 的服务管理器：启动程序，故障时重启，停机时关闭这一组进程。一个数据目录只能运行一个宿主，不能为了提高速度直接启动多个副本。

本模板限定 **单台 Linux 服务器、同机 Nginx、直接面向顾客**。不适用于 CDN、多层代理、不同机器网关、容器分离网关或多实例。测试时用容器运行 Nginx，但正式模板部署的是同机服务，不是 Docker Compose。

## 已经实现的保护

| 功能 | 现在的行为 |
|---|---|
| 域名检查 | 仅允许本机名称及明确配置的公开域名；其他 Host 被拒绝 |
| 代理来源 | 默认不信任任何代理；配置可信同机代理后，只使用它传入的单个 X-Real-IP |
| 伪造头 | Uvicorn 自动代理头解析关闭；客户端的 X-Forwarded-For/Forwarded 不用来决定应用限流身份 |
| 请求大小 | 网关与宿主均为 512 KiB；宿主检查实际收到的字节，分块上传也不能绕过 |
| 上传等待 | 请求体上传超过 15 秒会被拒绝；这不是模型回答超时 |
| 内部接口 | Nginx 不转发 `/internal` 与 `/internal/`；可信代理转来的内部请求也被宿主拒绝 |
| API 文档 | 正式模式关闭 `/docs`、`/redoc`、`/openapi.json`；网关同步屏蔽 |
| 网关限流 | 同一来源 IP 的站点、登录/访客创建、聊天有独立的频率上限，超限返回 429 |
| 模型保护 | 每日请求额度仍保存在数据库中，暂停和额度用完仍可联系人工 |

限流按来源 IP 统计，共用一个网络的人可能共享额度。应用访客创建仍为 10 次/小时/IP；网关登录和访客创建共享平均 10 次/分钟并允许少量突发。试运行后按正常顾客行为调整，不建议直接删除限制。网关的限流与应用的单进程限流会同时生效。

## 你现在可以先做的事

1. 初始化正式管理员，按《正式模式初始化与使用指南》启动独立正式库。
2. 填好真实店铺名称、服务时间、商品、政策；审核后发布。
3. 验证顾客咨询与人工回复；按《店铺运营与备份恢复操作指南》保存备份。
4. 提供服务器是否已准备、操作系统和域名。不要发送服务器密码、SSH 私钥或模型密钥。

没有服务器时，本机 8000/8001 链接只能在本机访问。公网部署后分享的是域名链接。

## 模板文件各管什么

| 文件 | 用途 |
|---|---|
| `deploy/nginx.conf.template` | 完整 Nginx 配置：HTTPS、跳转、代理与请求限制 |
| `deploy/shopagent.service` | Linux 服务启动、故障重启、进程组停止与写入目录限制 |
| `deploy/runtime.env.example` | 环境、数据目录、域名和代理配置，不含秘密 |
| `deploy/model.env.example` | 模型密钥文件的空模板，真实文件只能保存在服务器受保护位置 |
| `deploy/agent.production.toml.example` | 初始规则测试模式配置；之后按既有模型指南接 DeepSeek |

`YOUR_DOMAIN` 是占位文字，必须替换为真实域名。当前代码拒绝将它作为有效域名启动。不要把模板当作已配置的公网服务。

## 有服务器之后，按这个顺序操作

下面是部署执行流程。具体发行版、证书获取与防火墙命令需要服务器信息后确定；不直接在当前 Windows 电脑执行 Linux 安装命令。

### 第 1 步：准备目录和专用用户

在 Linux 服务器创建专用 `shopagent` 用户，并准备：

- `/opt/shopagent`：项目代码与虚拟环境，应用平时不写这里。
- `/var/lib/shopagent`：正式数据库、模块状态、模型配置；由 shopagent 用户管理。
- `/etc/shopagent`：运行配置和密钥环境文件；不要给其他用户读取权限。
- `/etc/shopagent/tls`：正式证书文件；私钥不可公开。
- `/var/www/acme`：证书 HTTP 校验文件目录。

项目要求 Python 3.12 或 3.13，现有 Windows 的 `.venv` 不能复制到 Linux。服务器建立新的虚拟环境并安装 `requirements.lock.txt`。上传代码时排除 `.env`、`.env.production`、`.venv`、演示 data、backups、test-results 和任何私钥。

### 第 2 步：配置独立正式环境

把 runtime.env.example 复制为 `/etc/shopagent/runtime.env`，替换域名，确认数据目录和模型配置路径。只信任同机 `127.0.0.1`，不要填写星号或外网地址。

把 model.env.example 复制为 `/etc/shopagent/model.env`。规则测试时密钥可为空；接入真实模型时，在服务器本地填写，不通过聊天发送。将该文件的读取权限限制为管理员和服务所需账户。

把初始模型配置放到 `/var/lib/shopagent/agent.production.toml`。先使用 mock 验证资料、登录和人工流程，再按模型指南启用 llm。切换模型模式会写这个配置文件，所以它必须在允许应用写入的目录。

### 第 3 步：初始化服务器上的正式管理员

初始化操作必须在服务器交互式终端进行，密码隐藏输入。使用相同的生产环境变量和数据目录，运行：

```bash
cd /opt/shopagent
export SHOPAGENT_ENV=production
export SHOPAGENT_DATA_DIR=/var/lib/shopagent
.venv/bin/python -m shopagent.admin_init
```

使用对该目录有权限的 shopagent 用户执行，避免生成 root 独占的数据库。不要把密码放在命令行。目录没有正式管理员时，服务不会通过生产启动校验。不要直接拷贝开发演示库替代初始化。

### 第 4 步：验证服务守护

将 shopagent.service 安装到 `/etc/systemd/system/shopagent.service`。由服务器管理员先检查单元配置，再加载和启动：

```bash
systemd-analyze verify /etc/systemd/system/shopagent.service
sudo systemctl daemon-reload
sudo systemctl enable --now shopagent
sudo systemctl status shopagent --no-pager
curl --fail http://127.0.0.1:8001/health
```

成功标准：正式模式健康响应，宿主和业务模块都只监听回环地址，程序只启动一个副本。故障时 service 采用 on-failure 重启；主动 stop 不会立即重启。备份期间使用 `systemctl stop shopagent`，不要在服务守护器仍会重启的情况下手动杀程序。

此服务单元尚未在你的 Linux 服务器启动验收；须检查 Python 路径、权限、数据目录和发行版支持。失败时先看脱敏后的错误，不反复重启绕过校验。

### 第 5 步：配置域名与证书

把域名解析到服务器，获得与该域名匹配的可信公网证书。模板要求证书放在 fullchain.pem 与 privkey.pem 指定的位置，配置证书续期并验证续期后 reload。

正式顾客不能使用本机测试证书。本机测试使用专用临时测试证书并验证它，不作为上线证书。

先准备证书再启用含 HTTPS 的完整模板，避免 Nginx 因缺少证书而无法启动。首次 HTTP 证书校验可先配置仅开放指定域名的校验目录，再启用完整模板；具体命令在确定服务器和证书方案后补齐。

### 第 6 步：启用 Nginx

替换模板的所有 YOUR_DOMAIN，确认后端固定为同机 `127.0.0.1:8001`。本文件是完整 nginx.conf，不能直接塞进另一个 http/server 块中。

先备份服务器现有 Nginx 配置。如果服务器已有其他网站，需要合并其配置，不能直接覆盖。执行语法检查成功后再 reload：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

公网只开放网页的 80/443，管理通道按你实际服务器方案保护。不要开放 8001 或动态模块端口。模板不支持直接把前面再加一个 CDN；那会改变可信来源和限流身份，需要另行配置验证。

### 第 7 步：外网验收

1. 手机切换移动网络，打开 `https://你的域名/customer`，证书正常、没有浏览器警告。
2. 商家登录 `/merchant`，不能使用演示账号或 demo123。
3. 顾客只看到已发布真实资料；两位顾客不能看到对方会话和工单。
4. 顾客登记人工咨询，商家回复，顾客能查看。
5. 暂停 AI 后仍能登记人工；额度达到上限后不再开始模型请求。
6. `/internal/invoke`、`/docs`、`/openapi.json` 返回 404；8001 和模块端口从外网不能直接连接。
7. 合理测试重启、备份恢复和模型故障，不做大规模压力测试。

外网验收完成后，才把顾客链接给少量试用用户。仍需补齐隐私告知、咨询保留/清理、错误监控和真实人工值守。

## 本机已经验证到哪一步

网关 ASGI 检查和本机宿主检查涵盖可信代理、伪造转发头、不同顾客限流隔离、请求实际字节上限与上传超时。

Nginx 官方镜像运行本机临时 HTTPS 代理，实测配置语法、证书验证、伪造头覆盖、内部入口屏蔽、非法 Host、超大请求 413、登录频率 429 和 HSTS。容器只发布到 `127.0.0.1`，验收后已关闭；没有创建公网链接。

Linux 服务单元、真实域名解析、公网证书续期、服务器防火墙和外网手机访问还没有实际验收。

## 配置依据

- [Uvicorn HTTP 设置](https://www.uvicorn.org/settings/#http)：默认代理头解析行为，本项目明确关闭并使用独立信任判断。
- [Nginx 代理头设置](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header)：网关覆盖 X-Real-IP，清除链式转发头。
- [Nginx 请求限流](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)：按来源限流、突发与 429 返回设置。
- [systemd 服务配置](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)：故障重启及服务生命周期。
